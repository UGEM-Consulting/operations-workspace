# IT onboarding — Milestone 5

## Approval and snapshot boundary

ReviewService creates the approval, authoritative employment assignments, immutable ItOnboardingRequest profile, checklist tasks and activity events using one EntityManager transaction. Failure anywhere rolls back the approval. Unique applicationId/approvalId constraints prevent duplicate requests; task request/key uniqueness prevents duplicate checklist entries. Historical approvals are untouched and are not automatically backfilled. A future approved historical-import process would need separate authorization and validation, especially where required American names/work phones are absent.

The snapshot contains only approved legal/American names, American display-name proposal, personal email, distinct personal/work phone values and final manager-approved employment details. It does not include draft revisions, internal review reasons, session identifiers or invitation credentials. Legal names are never replaced by American names. Snapshot fields are not editable from the IT API.

IT_SPECIALIST and SYSTEM_ADMIN may read/update requests. Every access checks the approved application and approval-decision relationship. Managers cannot operate IT endpoints; owner-scoped application review details expose a progress summary. Notifications are visible/readable only to their recipient. The existing global guard, active staff/session checks, exact Origin/JSON/non-simple-header CSRF checks, BFF allowlist and server secret remain authoritative.

## Request, checklist and contact state

The request belongs to an APPROVED application; the application remains APPROVED. Request status is derived: completedAt → COMPLETED; otherwise any Blocked task → BLOCKED; otherwise any non-Pending task → IN_PROGRESS; otherwise PENDING. There is no competing application status/approval flag.

The fixed manual checklist covers Google Workspace, Dispatch group membership, RingCentral, SMS, call recording, approved business software and the optional Equipment task (headset and laptop). Each task can be Pending, In Progress, Blocked or Completed until request completion; the optional Equipment task can also be Not needed, which counts as done. Migration `OptionalEquipmentTask1792740000000` adds a pending Equipment task to open requests only; completed requests keep their original six tasks, and its rollback refuses to discard any recorded Equipment outcome. Blocked needs a reason (the existing notes or new ones). A task update without `notes` keeps the recorded notes; an empty string clears them. An unknown task, or an optional task missing from an older request, returns 404. Request progress (Pending, In Progress, Blocked, Completed) has one definition in `it.entity.ts`, used for both the queue filter (SQL) and the detail view. This records manual fictional attestations, not external account/API operations or evidence that real services were configured. Business-software authorization remains a manual company policy process recorded in task notes. Notes must never contain credentials.

The applicant work phone is displayed as Applicant Provided until an IT/admin user explicitly records verification. Actor and timestamp are stored. The actual assigned RingCentral number is a separate validated field and may equal or differ from the applicant work phone. Neither contact updates nor checklist changes overwrite personal/work numbers in the snapshot/application. RingCentral cannot be completed without its assigned number; the last task cannot complete the request until work-phone verification and an assigned number exist.

All updates lock the request, reject stale expected versions and increment version. Completed requests are immutable for every role. Status, contact-verification and completion events retain actor/time with metadata; phone values and free-text notes are not copied into audit payloads. Existing application/review histories remain intact.

## Completion and portal notices

The final task update, completedAt, IT/application activity and a unique PortalNotification for the responsible manager commit together. Concurrent/repeated final updates cannot create multiple completions or notifications. A completed request cannot be reopened. Manager dashboard notices appear on page refresh and can be marked read; this is a durable in-portal notice, not an email/SMS/realtime delivery claim. Lists show the most recent 50 notifications and total unread count. Admin reviewers do not redirect a notification away from the owning/assigned manager.

## Removal when a dispatcher leaves

Someone added by hand (see docs/dispatcher-onboarding.md) has no setup request: their checklist uses the accounts their manager recorded, says No IT setup on record, and shows Not recorded for anything missing. Check the admin consoles too. A support added by hand gets a checklist only if accounts were recorded for them.

Approved 2026-11-02 (Design System: MarkAsLeftScreen, ItRemovalScreen, ItTasksQueueScreen, LeftDispatcherScreen). Marking a dispatcher who ever had a setup request as left opens an IT removal request in the same transaction: the reverse of setup, due by the end of their last day, with a snapshot of what to remove (display name, company email, RingCentral number, MC and team) and the manager's choice for the company email (forward new mail to them for 30 days, or suspend only). The checklist is Google Workspace (suspend and sign out everywhere), Dispatch group, RingCentral (remove the user with SMS and call recording; record whether the number is kept for the next dispatcher, forwarded to the team or released), business software, shared passwords and optional equipment. A setup that hadn't finished is cancelled and leaves the queue; whatever IT had already created is on the removal checklist. Every active IT specialist gets the Telegram alert "Access to remove". Finishing the last task sends the manager who marked them as left a portal notice (IT access removed). Removals follow the setup rules: manual records, version-checked writes, notes for blocked tasks, no passwords or tokens in notes, metadata-only activity. IT tasks lists setups and removals together, open removals first.

A manager can record notice for a future last day (up to 90 days ahead) while the dispatcher keeps working. The removal then shows as Scheduled, on its own tab and out of Removals due: IT can plan, add notes and mark tasks in progress, but tasks can be marked completed only from the last day. IT is alerted when notice is recorded and again on the last day. A manager can change the date (the checklist moves), cancel the notice while IT hasn't started (the checklist is cancelled) or ask to remove access now (due today, with its own alert). Removal never waits for drivers or supports to be reassigned, though the dispatcher's record stays Leaving until they are.

## Persistence and deployment

ItOnboarding1792650000000 creates it_onboarding_requests, it_onboarding_tasks, it_onboarding_activity and portal_notifications with UUID foreign keys, uniqueness, timestamps and indexes. Runtime/CLI entities are registered in the shared TypeORM options. Synchronization and TypeORM migrationsRun remain disabled. Render start:render applies pending migrations before starting the API; other release methods must apply migrations explicitly. Down refuses to drop any IT request/history; rollback after use requires a reviewed recovery plan. Disposable-test checks truncate only an explicitly selected local *_test database.

No new secrets/dependencies, cloud resources or external accounts are required for this manual workflow; the removal checklist (DispatcherOffboarding1792950000000) is manual too. Next.js and NestJS retain independent builds and the same-origin production cookie boundary for Vercel/Render. Production applicant verification emails codes over SMTP (see email-delivery.md) and fails closed without it. Production staff/demo account provisioning, environment setup, backup/retention, dependency advisory review, edge limits and interactive browser QA remain prerequisites for a hosted demonstration or broader use.
