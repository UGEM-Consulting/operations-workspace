# Operations Workspace engineering guide

## Scope and architecture
Milestone 5 adds manual IT onboarding requests/checklists and manager portal completion notifications to the existing review workflow. NestJS owns all business logic, validation, and PostgreSQL access. Next.js owns presentation and server-side HTTP calls to the API. Never import API code into the frontend or connect a browser to the database. Do not create external accounts, integrate external messaging/provisioning, collect documents, or reopen approved/rejected applications without a separately authorized future scope.

## Repository
- `apps/web/src/app`: App Router routes and layouts; Server Components by default.
- `apps/web/src/components`: reusable shell and shadcn/ui components.
- `apps/web/src/features`: feature-specific presentation.
- `apps/web/src/lib`: small framework helpers and server-only API client.
- `apps/api/src/common`: shared HTTP configuration.
- `apps/api/src/config`: validated environment configuration.
- `apps/api/src/database`: TypeORM options, CLI data source, identity migrations and demo seed.
- `apps/api/src/modules`: bounded NestJS modules; health, identity, authentication, internal user management and onboarding.
- `packages/shared`: reserved for future transport contracts, not business logic or entities.

## Conventions
Use strict TypeScript, small cohesive modules, clear names, and existing patterns. Keep Client Components limited to interactivity. Use npm workspaces and one root package-lock.json. Run npm installation at the repository root. Avoid unnecessary abstractions and dependencies. No Prisma, Firebase, Supabase, or Turborepo. Support Node 22.12+ (22.x) for local development and Node 24 LTS for deployment. Run `npm run typecheck`, `npm run lint`, `npm test`, and `npm run build` after meaningful changes. Test behavior and failure boundaries rather than implementation details.

## Security
Never commit secrets or log connection strings and sensitive records. Keep API_BASE_URL server-only. Validate all API DTOs and new environment settings. Use explicit CORS origins; CORS is not authentication. Use the global deny-by-default NestJS guard. Protected endpoints require explicit role metadata. Public decorators require a specific reviewed reason. Current role/status must be loaded from PostgreSQL; UI navigation is not authorization. Use fictional data only. Never implement real document uploads in this milestone. Use Argon2id and express-session with PostgreSQL; do not invent session cryptography. All browser mutations go through the allowlisted same-origin Next.js BFF with exact Origin, JSON and non-simple-header CSRF checks; NestJS independently checks them and the server-only BFF secret. Never store authentication tokens in localStorage. Keep Secure/HttpOnly/host-only production cookies. Revoke sessions on role/status/password changes and preserve the last active administrator. Do not print credentials, session IDs, hashes, or raw database error details. TypeORM synchronize and migrationsRun must remain false in every environment. The explicit start:render wrapper is authorized to apply reviewed pending migrations before starting the API; ordinary start/dev and builds must not migrate. Verify TLS certificates when using external PostgreSQL connections.

## Expansion and deployment
Add business capabilities in focused NestJS modules and matching frontend feature folders. Share transport contracts only when actual duplication warrants a package. Do not duplicate business rules. Future entities must be registered explicitly in the common TypeORM options so runtime and CLI agree. Vercel builds web; Render builds API; neither should require the other to build. Do not deploy or create cloud resources without explicit authorization. Keep the health endpoint free of credentials and implementation details.

## Identity development and tests
Use `npm run setup:local`, explicit migrations, and `npm run seed:demo` for fictional local accounts. Seed only non-production `example.test` addresses with environment-supplied/generated passwords. Never reset existing accounts during an idempotent seed. Auth integration tests require a dedicated `TEST_DATABASE_URL` ending in `_test` and intentionally truncate identity and dependent onboarding tables only in that selected database. Run both default tests and PostgreSQL integration tests for auth changes. Keep the same-origin proxy limited to approved endpoints and do not add business permission matrices to Next.js. Backend `/auth/me` supplies navigation and landing destinations.

## Future identity flows
Read `docs/identity-architecture.md` before adding applicant access or SSO. Applicants are separate from staff. Invitation tokens must be random, hashed at rest, expiring, atomically consumed, and never reused for corrections. Managers need object-level authorization against database-loaded assignments. Google SSO should map verified issuer/subject identities to existing staff and retain server-owned roles, status and session revocation.

## Applicant workflow conventions
Applicants are separate from User. The existing express-session library uses a separate applicant cookie and PostgreSQL store; never treat an applicant cookie as staff identity. Applicant controllers bypass only the staff guard and must call the service session/record check. Keep the BFF secret, exact Origin, JSON and CSRF header requirements for applicant mutations. Never put invitation tokens in API paths, logs, analytics, or persistent browser storage. Development incoming request logging is disabled because /apply/[token] contains a credential; production edge/APM logs must redact these URLs before enabling external verification delivery.

Store invitation token hashes only; return the raw link once on creation. Consume the token atomically after verification. Returning drafts use application reference + independently verified email, never reuse a consumed invitation. Local verification is development/test only, fictional example.test addresses only, and codes are delivered exclusively through the explicit private terminal command. Production verification fails closed until an approved delivery service exists.

Load assignments from PostgreSQL and enforce owner-or-admin policy on every manager record access. Managers cannot read draft personal answers. Serialize invitation revocation/draft/submission against the invitation row. Enforce optimistic draft version checks, a unique application per invitation, and explicit state transitions; duplicate submission retries must not change data or append another submission event. Audit rows contain event metadata, not field values or credentials. Never add real document collection. Read docs/dispatcher-onboarding.md for current access, retention and deployment limitations.

## Review workflow conventions
`DispatcherApplication.status` remains the only current workflow state. Use the explicit transition policy; initial submissions must pass through DRAFT. Draft saves do not transition DRAFT or CHANGES_REQUESTED. Review writes, applicant saves and resubmissions lock the invitation first, re-read the application, and validate its version. Do not bypass these locks or add direct status-edit endpoints. APPROVED and REJECTED are terminal even for administrators.

Review decisions are append-only through the API and contain reviewer ID, decision, reason, requested fields, prior/new status and version. Their createdAt is the approval/rejection timestamp; do not add a competing approval flag. `readyForIt` is derived from APPROVED, never separately mutable. ApplicationSubmission stores only submitted personal-field revisions for comparison; never put these values in audit-event payloads. Managers must see the latest submitted revision while a correction draft is in progress. Applicant responses use an explicit safe projection: only active correction instructions/fields, never internal approval/rejection notes or staff review histories.

Correction fields include personal fields plus applicant-provided MC, team lead and job title. Verified email remains immutable. Managers finalize authoritative employment assignments in the version-checked approval action; never copy applicant employment directly into manager-controlled invitation assignment columns. A change request grants a 30-day applicant access window separate from the already-consumed invitation token. Return access still requires a valid applicant session or fresh email verification. Production verification remains disabled. Review actions require owner/admin scope, confirmation for approve/reject, reasons for reject/change requests, explicit version, CSRF and rate limiting. IT can access the approved onboarding projection/checklist only; it cannot access generic applications, drafts, review decisions or internal comments.

The review queue uses server-side scoped search/sort/pagination; dashboard summaries count all authorized records. Notification-ready events are recorded transactionally in existing ApplicationActivity and surfaced as review queues/correction notices. Do not claim external delivery. Review migration rollback refuses to discard existing decisions or advanced workflow states. Use the explicit disposable-database verification script only on local *_test databases.

## Simplified invitation claiming
The primary Create Invitation action immediately returns a unique link without applicant details; the API also accepts an empty JSON object. Expected email is optional; expiration defaults to seven days and may be changed. Legacy employment input remains accepted for compatibility but is not collected by the manager UI. New invitation email is unbound until successful verification; expectedEmail is a distinct optional restriction.

Every verification challenge stores the exact normalized email being verified. Do not bind an open invitation in begin(), and do not accept an email override in verify(). Under the existing invitation row lock, verify() must recheck the expected email, expiration, revocation and consumed state, then set the verified email and consume the invitation atomically. Concurrent claimants must yield exactly one successful identity and retain the existing unique application per invitation. Resume still requires the bound email, application reference and fresh verification; production demo bypasses remain disabled.

Applicants enter personal email before verification and complete employment in ApplicationFields. Submitted revisions include employment. Approval requires explicit employmentConfirmed plus validated final MC/teamLead/jobTitle, writes authoritative invitation assignments in the same transaction, records previous/final assignments on ApplicationReview and emits EMPLOYMENT_CONFIRMED. Existing approved records remain approved. Never mutate submitted applicant answers to hide a manager assignment correction. Migration backfills legacy details into working/submitted fields without overwriting existing keys, preserves pending challenges and refuses lossy downgrade of simplified data.

## Required applicant contact/display-name data
Canonical JSONB application/submission fields are personalPhoneNumber, workPhoneNumber, preferredAmericanFirstName and preferredAmericanLastName. First/last-name UI labels omit Legal; IT data retains those legal names separately. Personal phone and both American names are required for submission, resubmission and approval; applicant work phone is optional. New application forms omit the work phone input unless a saved legacy value or explicit correction request exists. IT records the assigned work number separately during RingCentral setup. Validate a work phone when supplied; never require a missing one. Drafts may be incomplete. Trim names and reject whitespace-only values. Use the same documented structural phone contract in Zod/DTOs/merged-field checks: 7–15 digits, optional leading + and common separators, max 40 characters. Never infer a work phone from a personal phone.

Legacy migrations copy original phone/preferred-name values into canonical keys without placeholders or status changes. Keep historical approved records accessible and approved. Correction requests include required missing fields, and existing correction rounds derive additional completion fields from the last submitted revision so saved corrections remain editable. Never use unsent correction drafts to satisfy a manager approval. ReviewService checks required data transactionally before recording new approvals. Applicant drafts still use optimistic versions and record locks.

Review responses include missing-field metadata and an itDetails projection with legal names, phones, American names and a nullable proposedDisplayName derived only from complete American names. Do not substitute the legal name when American names are absent, overwrite legal names, expand IT access beyond the approved onboarding projection, or provision external accounts. The new data migration's rollback retains collected work/canonical JSON values; migration checks must use a local disposable *_test database with explicit opt-in.

## IT onboarding and portal notifications
New approvals create exactly one ItOnboardingRequest and the six fixed checklist tasks in the same EntityManager transaction as the review and audit events. Unique application/approval/task keys are mandatory. Never commit approval if request/checklist creation fails. Historical approvals are preserved and are not automatically queued by the migration. Do not change application approval status to represent IT task progress: APPROVED remains the manager review result, while IT request progress is derived from its tasks and terminal completedAt.

The IT profile is an immutable approved snapshot: American names/display name, separate legal names, personal/work phones, personal email and final manager-approved MC/team lead/job title. Do not copy internal reviewer comments, applicant session credentials, invitation tokens or draft answers. IT/admin are the only checklist readers/writers; managers receive scoped progress through their own application detail and notifications. Recheck the approved application/decision relationship on IT access.

Keep applicant work phone, IT verification actor/timestamp and actual assigned RingCentral number separate. Mark the work phone Applicant Provided until explicit manual IT verification. Group RingCentral, SMS and call recording in one RingCentral UI section while preserving all six task keys, individual statuses, notes and audit history. Completion requires six Completed tasks and the assigned RingCentral number. Verify the legacy applicant work phone only if a nonblank value exists; missing applicant work phone must never block IT completion. All request writes lock the request row, require version, increment version and audit metadata only. Blocked tasks require notes. Completed requests cannot be edited/reopened. Do not put passwords/tokens in notes or duplicate phone values into audit metadata.

The final task, completion timestamp, activity events and exactly one PortalNotification for the responsible manager must commit atomically. Notifications are recipient-scoped and read acknowledgements cannot access another user's records. All new routes use explicit role metadata and the existing CSRF/BFF/session boundary. The IT migration refuses rollback if any IT requests exist; only run migration-check resets on an explicitly selected local disposable *_test database. No new cloud resources, external accounts or messages are authorized.

## First administrator bootstrap
`admin:bootstrap` is an explicit operator-only compiled CLI, never a route, migration, startup hook or build hook. Preserve the production ban and fictional-only restrictions on seed:demo. Reuse User, validateEnvironment, databaseOptions and hashPassword. Accept BOOTSTRAP_ADMIN_EMAIL/FIRST_NAME/LAST_NAME; normalize/validate identity and get the 12–128 character password only through the hidden, confirmed interactive prompt. No password env variable, command argument, pipe, raw errors or sensitive output. Any existing SYSTEM_ADMIN (including inactive) refuses bootstrap; existing emails must never be elevated/reset/reactivated. Keep the shared administrator advisory lock then SHARE ROW EXCLUSIVE users lock and insert inside one READ COMMITTED transaction. Never replace this with a count outside the transaction.

Execution: Node 24, reviewed migrations already applied, API compiled, all normal validated API environment variables plus BOOTSTRAP_ADMIN_* identity configured. On a paid Render interactive Shell, from repository root run `npm run admin:bootstrap` and answer the hidden prompts. For Render Free, build locally with `npm ci` and `npm run build --workspace=@operations/api`, create/chmod 600 a Git-ignored root `.env.admin-bootstrap` containing normal API configuration and bootstrap identity (no administrator password), then run `DOTENV_CONFIG_PATH=../../.env.admin-bootstrap npm run admin:bootstrap` from root. Use the external database DNS URL, DATABASE_SSL=true, no URL SSL overrides, and temporary narrowly scoped external IP access; restore restrictions/remove the private file afterward. Existing exported variables override dotenv, so use a clean terminal. This CLI requires verified TLS for non-local hosts, including a paid Render shell using an external URL. Do not disable TLS verification for internal self-signed certificates. Full exact instructions and supported Render methods are in README.md. No production account/database action is authorized during implementation/testing. Use a disposable *_test database for bootstrap integration tests, including concurrent executions and existing-user preservation.

## Render migration startup
The user explicitly requested automatic pending migrations on Render, including Free. Use `npm run start:render --workspace=@operations/api` in Render and render.yaml. start-render awaits the locked deploy-migrations runner before importing main; never start the API on migration failure. migration:run:prod uses the same runner. Hold the PostgreSQL session advisory lock 42002027 across TypeORM history checks and the complete all-migrations transaction, on the same QueryRunner connection as MigrationExecutor, using a one-connection migration pool. Never run migrations on a separate connection from the lock. Use deploymentMigrationLogger to suppress TypeORM migration messages (logging=false alone still emits raw migration errors). Always release/destroy connections, sanitize errors, and keep the 60-second deployment statement timeout separate from normal API queries. Keep TypeORM synchronize/migrationsRun false. Ordinary start/dev/build/seed/bootstrap behavior is unchanged; no automatic accounts. Use additive, previous-version-compatible migrations because Render may overlap old/new instances; no automatic rollback. Test skip-on-restart, overlapping runners, rollback/lock release, and startup blocked on failure in isolated test schemas in a dedicated *_test database. Do not connect to production or deploy as part of implementing/testing startup changes.

## Frontend backend connectivity
The BFF permits up to 90 seconds per upstream request and declares maxDuration=120 for Render Free wakeup; use Vercel Fluid Compute. Never retry mutations automatically, relax CSRF, or bypass sessions to mask outages. readBackendConfig validates HTTPS origins in production (no path, credentials, query or fragment) and header-safe BFF secret formatting. Logs must contain only allowlisted backendFailureCode results, never exception objects/messages, environment values, paths containing applicant tokens, credentials or cookies. Runtime logs distinguish configuration, timeout, network and generic failures. Changes require frontend redeployment; do not deploy without authorization. Longer proxy deadlines cannot fix an unavailable Render service and authenticated SSR retains its separate bounded timeout.
