# Operations Workspace engineering guide

## Scope and architecture
Milestone 5 adds manual IT onboarding requests/checklists and manager portal completion notifications to the existing review workflow. NestJS owns all business logic, validation, and PostgreSQL access. Next.js owns presentation and server-side HTTP calls to the API. Never import API code into the frontend or connect a browser to the database. The workspace is moving to production with real staff and applicant data. Applicant verification email over SMTP (Google Workspace) is authorized; see "Production email delivery" below. Do not create external accounts, integrate other external messaging/provisioning, collect documents beyond the authorized onboarding photos and e-signatures (see "Onboarding documents and e-signatures"), or reopen approved/rejected applications without a separately authorized future scope.

## Repository
- `apps/web/src/app`: App Router routes and layouts; Server Components by default.
- `apps/web/src/components`: reusable shell and shadcn/ui components.
- `apps/web/src/features`: feature-specific presentation.
- `apps/web/src/lib`: small framework helpers and server-only API client.
- `apps/api/src/common`: shared HTTP configuration.
- `apps/api/src/config`: validated environment configuration.
- `apps/api/src/database`: TypeORM options, CLI data source, identity migrations and demo seed.
- `apps/api/src/modules`: bounded NestJS modules; health, identity, authentication, internal user management and onboarding.
- `packages/shared`: reserved for future transport contracts, not business logic or entities.

## Conventions
Use strict TypeScript, small cohesive modules, clear names, and existing patterns. Keep Client Components limited to interactivity. Use npm workspaces and one root package-lock.json. Run npm installation at the repository root. Avoid unnecessary abstractions and dependencies. No Prisma, Firebase, Supabase, or Turborepo. Support Node 22.12+ (22.x) for local development and Node 24 LTS for deployment. Run `npm run typecheck`, `npm run lint`, `npm test`, and `npm run build` after meaningful changes. Test behavior and failure boundaries rather than implementation details.

## Security
Never commit secrets or log connection strings and sensitive records. Keep API_BASE_URL server-only. Validate all API DTOs and new environment settings. Use explicit CORS origins; CORS is not authentication. WEB_ORIGIN and CORS_ORIGINS are comma-separated lists of exact literal-host origins (no paths or wildcards, HTTPS in production). The BFF and NestJS each accept a mutation only when its Origin exactly equals one listed WEB_ORIGIN, and the BFF forwards that validated origin. The first WEB_ORIGIN is the primary origin for generated links. Session cookies stay host-only, so each domain has its own sign-in. Use the global deny-by-default NestJS guard. Protected endpoints require explicit role metadata. Public decorators require a specific reviewed reason. Current role/status must be loaded from PostgreSQL; UI navigation is not authorization. Use fictional data only in development, tests, seeds and the demo deployment; production holds real personal data, so never copy it into logs, tests, fixtures or non-production databases. Uploads are limited to the authorized onboarding photos, company PDFs, driver document scans, driver MVRs (screening and yearly), driver consent form PDFs, notice letter PDFs, owner-operators' lease, insurance and registration PDFs (authorized 2026-11-06) and scans of an NDA or SOP signed on paper by someone added by hand (authorized 2026-11-11; see "Trusted devices and paper scans") in private storage (see "Onboarding documents and e-signatures" and "Safety drivers"). Use Argon2id and express-session with PostgreSQL; do not invent session cryptography. All browser mutations go through the allowlisted same-origin Next.js BFF with exact Origin, JSON and non-simple-header CSRF checks; NestJS independently checks them and the server-only BFF secret. Never store authentication tokens in localStorage. Keep Secure/HttpOnly/host-only production cookies. Revoke sessions on role/status/password changes and preserve the last active administrator. Do not print credentials, session IDs, hashes, or raw database error details. TypeORM synchronize and migrationsRun must remain false in every environment. The explicit start:render wrapper is authorized to apply reviewed pending migrations before starting the API; ordinary start/dev and builds must not migrate. Verify TLS certificates when using external PostgreSQL connections. validateEnvironment refuses DATABASE_URL ssl/sslmode/sslcert/sslkey/sslrootcert/sslpassword/sslaccept parameters everywhere, and production requires DATABASE_SSL=true unless the host is localhost or a dotless private hostname (Render internal URL). Staff login limits use hashed login_attempts keys: per BFF-forwarded client IP (x-client-ip, trusted only with the BFF secret) 100/15 min, per email+IP 10/15 min, per email 20 failures/15 min and a 1000/min circuit breaker; a correct password clears the email and email+IP counters. Keep the dummy hash and identical responses. Swagger is mounted only outside production. The API sets nosniff, X-Frame-Options DENY, Referrer-Policy no-referrer, CORP same-origin and a default Cache-Control no-store, and disables x-powered-by; the web app sets a partial CSP (frame-ancestors/object-src/base-uri/form-action), X-Frame-Options, nosniff, Permissions-Policy and production HSTS. A strict script-src needs per-request nonces and is a separate change. main.ts exports bootstrap; start-render awaits it in its sanitised catch.

## Expansion and deployment
Add business capabilities in focused NestJS modules and matching frontend feature folders. Share transport contracts only when actual duplication warrants a package. Do not duplicate business rules. Future entities must be registered explicitly in the common TypeORM options so runtime and CLI agree. Vercel builds web; Render builds API; neither should require the other to build. Do not deploy or create cloud resources without explicit authorization. Keep the health endpoint free of credentials and implementation details.

## Identity development and tests
Use `npm run setup:local`, explicit migrations, and `npm run seed:demo` for fictional local accounts. Seed only non-production `example.test` addresses with environment-supplied/generated passwords. Never reset existing accounts during an idempotent seed. Auth integration tests require a dedicated `TEST_DATABASE_URL` ending in `_test` and intentionally truncate identity and dependent onboarding tables only in that selected database. Run both default tests and PostgreSQL integration tests for auth changes. Keep the same-origin proxy limited to approved endpoints and do not add business permission matrices to Next.js. Backend `/auth/me` supplies navigation and landing destinations.

## Future identity flows
Read `docs/identity-architecture.md` before adding applicant access or SSO. Applicants are separate from staff. Invitation tokens must be random, hashed at rest, expiring, atomically consumed, and never reused for corrections. Managers need object-level authorization against database-loaded assignments. Google SSO should map verified issuer/subject identities to existing staff and retain server-owned roles, status and session revocation.

## Applicant workflow conventions
Applicants are separate from User. The existing express-session library uses a separate applicant cookie and PostgreSQL store; never treat an applicant cookie as staff identity. Applicant controllers bypass only the staff guard and must call the service session/record check. Keep the BFF secret, exact Origin, JSON and CSRF header requirements for applicant mutations. Never put invitation tokens in API paths, logs, analytics, or persistent browser storage. Invitation links are /apply#<token>: the URL fragment is never sent to servers, so tokens cannot reach hosting, CDN or APM request logs or Referer headers; the page holds the token in memory and strips it from the address bar. The legacy /apply/[token] path route has been removed (production only ever issued fragment links); development incoming-request logging stays disabled.

Store invitation token hashes only; return the raw link once on creation. Consume the token atomically after verification. Returning drafts use application reference + independently verified email, never reuse a consumed invitation. Without EMAIL_DELIVERY=smtp, local verification is development/test only, fictional example.test addresses only, and codes are delivered exclusively through the explicit private terminal command; production verification then fails closed. With EMAIL_DELIVERY=smtp, codes are emailed (see "Production email delivery"). Verification rate limits are per client IP (IPv6 /64), per email+IP and per invitation-or-reference+IP; there is no cap shared by every holder of a link, so a forwarded link cannot block the real applicant; global counters are high circuit breakers only (BEGIN_LIMITS/VERIFY_LIMITS in onboarding/rate-limit.ts). Counters key only on request input so matched and unmatched requests write identically. After the response, matched sends are capped per recipient per day, per distinct address per open invitation per day, and by a daily budget (SEND_LIMITS); a refused send keeps the identical response and records VERIFICATION_EMAIL_FAILED with a safe code.

Load assignments from PostgreSQL and enforce owner-or-admin policy on every manager record access. Managers cannot read draft personal answers. Serialize invitation revocation/draft/submission against the invitation row. Enforce optimistic draft version checks, a unique application per invitation, and explicit state transitions; duplicate submission retries must not change data or append another submission event. Audit rows contain event metadata, not field values or credentials. Collect no documents beyond the onboarding photos and signatures below. Read docs/dispatcher-onboarding.md for current access, retention and deployment limitations.

## Review workflow conventions
`DispatcherApplication.status` remains the only current workflow state. Use the explicit transition policy; initial submissions must pass through DRAFT. Draft saves do not transition DRAFT or CHANGES_REQUESTED. Review writes, applicant saves and resubmissions lock the invitation first, re-read the application, and validate its version. Do not bypass these locks or add direct status-edit endpoints. The transition policy also allows CHANGES_REQUESTED → REJECTED, so a manager can close an application whose corrections are outstanding. It keeps every rejection requirement, locks the invitation first, records previousStatus CHANGES_REQUESTED, cuts applicantAccessUntil to at most 7 days and queues the REJECTED update. Approval still requires a resubmission. APPROVED and REJECTED are terminal even for administrators.

Review decisions are append-only through the API and contain reviewer ID, decision, reason, requested fields, prior/new status and version. Their createdAt is the approval/rejection timestamp; do not add a competing approval flag. `readyForIt` is derived from APPROVED, never separately mutable. ApplicationSubmission stores only submitted personal-field revisions for comparison; never put these values in audit-event payloads. Managers must see the latest submitted revision while a correction draft is in progress. Applicant responses use an explicit safe projection: only active correction instructions/fields, never internal approval/rejection notes or staff review histories.

Correction fields include personal fields plus applicant-provided MC, team lead and job title. Verified email remains immutable. Managers finalize authoritative employment assignments in the version-checked approval action; never copy applicant employment directly into manager-controlled invitation assignment columns. A change request grants a 30-day applicant access window separate from the already-consumed invitation token. Return access still requires a valid applicant session or fresh email verification. Review actions require owner/admin scope, confirmation for approve/reject, reasons for reject/change requests, explicit version, CSRF and rate limiting. IT can access the approved onboarding projection/checklist only; it cannot access generic applications, drafts, review decisions or internal comments.

The review queue uses server-side scoped search/sort/pagination; dashboard summaries count all authorized records. Notification-ready events are recorded transactionally in existing ApplicationActivity and surfaced as review queues/correction notices. Do not claim external delivery. Review migration rollback refuses to discard existing decisions or advanced workflow states. Use the explicit disposable-database verification script only on local *_test databases.

## Simplified invitation claiming
The primary Create Invitation action immediately returns a unique link without applicant details; the API also accepts an empty JSON object. Once the applicant verifies their email, the invitations list adds applicationReference (the application's id, never its answers) so the manager can copy it on Invitations while the applicant is still filling in the form (InvitationReferenceScreen, approved 2026-11-09). Expected email is optional; expiration defaults to seven days and may be changed. Legacy employment input remains accepted for compatibility but is not collected by the manager UI. New invitation email is unbound until successful verification; expectedEmail is a distinct optional restriction.

Every verification challenge stores the exact normalized email being verified. Do not bind an open invitation in begin(), and do not accept an email override in verify(). Under the existing invitation row lock, verify() must recheck the expected email, expiration, revocation and consumed state, then set the verified email and consume the invitation atomically. Concurrent claimants must yield exactly one successful identity and retain the existing unique application per invitation. Resume still requires the bound email, application reference and fresh verification; production demo bypasses remain disabled.

Applicants enter personal email before verification and complete employment in ApplicationFields. Submitted revisions include employment. Approval requires explicit employmentConfirmed plus validated final MC/teamLead/jobTitle, writes authoritative invitation assignments in the same transaction, records previous/final assignments on ApplicationReview and emits EMPLOYMENT_CONFIRMED. Existing approved records remain approved. Never mutate submitted applicant answers to hide a manager assignment correction. Migration backfills legacy details into working/submitted fields without overwriting existing keys, preserves pending challenges and refuses lossy downgrade of simplified data.

## Required applicant contact/display-name data
Canonical JSONB application/submission fields are personalPhoneNumber, workPhoneNumber, preferredAmericanFirstName and preferredAmericanLastName. First/last-name UI labels omit Legal; IT data retains those legal names separately. Personal phone and both American names are required for submission, resubmission and approval; applicant work phone is optional. Work phones are assigned by IT, so applicant and manager UIs no longer collect or request an applicant work phone; the input appears only when a correction lists it (an invalid legacy value). The API still accepts the field for legacy records and older deployed clients. IT records the assigned work number separately during RingCentral setup. Validate a work phone when supplied; never require a missing one. Drafts may be incomplete. Trim names and reject whitespace-only values. Use the same documented structural phone contract in Zod/DTOs/merged-field checks: 7–15 digits, optional leading + and common separators, max 40 characters. Never infer a work phone from a personal phone.

Legacy migrations copy original phone/preferred-name values into canonical keys without placeholders or status changes. Keep historical approved records accessible and approved. Correction requests include required missing fields, and existing correction rounds derive additional completion fields from the last submitted revision so saved corrections remain editable. Never use unsent correction drafts to satisfy a manager approval. ReviewService checks required data transactionally before recording new approvals. Applicant drafts still use optimistic versions and record locks.

Review responses include missing-field metadata and an itDetails projection with legal names, phones, American names and a nullable proposedDisplayName derived only from complete American names. Do not substitute the legal name when American names are absent, overwrite legal names, expand IT access beyond the approved onboarding projection, or provision external accounts. The new data migration's rollback retains collected work/canonical JSON values; migration checks must use a local disposable *_test database with explicit opt-in.

## IT onboarding and portal notifications
New approvals create exactly one ItOnboardingRequest and the fixed checklist tasks (six required plus the optional Equipment task) in the same EntityManager transaction as the review and audit events. Unique application/approval/task keys are mandatory. Never commit approval if request/checklist creation fails. Historical approvals are preserved and are not automatically queued by the migration. Do not change application approval status to represent IT task progress: APPROVED remains the manager review result, while IT request progress is derived from its tasks and terminal completedAt.

The IT profile is an immutable approved snapshot: American names/display name, separate legal names, personal/work phones, personal email and final manager-approved MC/team lead/job title. Do not copy internal reviewer comments, applicant session credentials, invitation tokens or draft answers. IT/admin are the only checklist readers/writers; managers receive scoped progress through their own application detail and notifications. Recheck the approved application/decision relationship on IT access, including the IT photo, with the shared approvedApplication() check. Task notes are optional on update: omitted keeps the recorded notes, '' clears them. IT status comes from the single rule table in it.entity.ts (itStatus/itStatusSql). The web records the company email in the Google Workspace task dialog and the assigned RingCentral number in the RingCentral task dialog (that field first: until it is filled the task may be Not started, In progress or Blocked, and Completed unlocks once it is, as the API requires); it saves the account through the contact route, then the task with the returned version.

Keep applicant work phone, IT verification actor/timestamp and actual assigned RingCentral number separate. Mark the work phone Applicant Provided until explicit manual IT verification. Group RingCentral, SMS and call recording in one RingCentral UI section while preserving all task keys, individual statuses, notes and audit history. Completion requires every required task Completed, the optional Equipment task Completed or Not needed (NOT_NEEDED is allowed only for optional tasks and enforced by a CHECK), the assigned RingCentral number and the company (Google Workspace) email IT created; completing the Google Workspace task also requires that email. CompanyEmail1792700000000 adds the column with a NOT VALID completion CHECK so historical completed requests stay intact, and its rollback refuses to discard recorded emails. The responsible manager's application detail shows these company accounts as Employee details; never expose IT notes or verification metadata there. Verify the legacy applicant work phone only if a nonblank value exists; missing applicant work phone must never block IT completion. All request writes lock the request row, require version, increment version and audit metadata only. Blocked tasks require notes. Completed requests cannot be edited/reopened. Do not put passwords/tokens in notes or duplicate phone values into audit metadata.

The final task, completion timestamp, activity events and exactly one PortalNotification for the responsible manager must commit atomically. Notifications are recipient-scoped and read acknowledgements cannot access another user's records. All new routes use explicit role metadata and the existing CSRF/BFF/session boundary. The IT migration refuses rollback if any IT requests exist; only run migration-check resets on an explicitly selected local disposable *_test database. No new cloud resources or external accounts are authorized; the messages allowed are listed under "Notifications" below.

## Staff multi-factor authentication
Staff (not applicants) use TOTP authenticator apps via the maintained `otpauth` library (never hand-rolled TOTP), or email codes (authorized 2026-10-29), plus ten single-use recovery codes. SYSTEM_ADMIN always requires MFA. The singleton staff_security_settings policy (ADMINS or ALL_STAFF) can only add roles, and other roles may opt in. Read the README section "Staff two-step verification".

A correct password for an enrolled or required user stores only `session.mfaPending` (userId, authVersion, stage verify/enrol, short expiry). Never set `session.userId` before the second step. The global guard admits a pending session only on routes with `@AllowPendingMfa(stage)`, which still need `@Roles` and must re-read the pending state in the service. Full sessions record `mfa: 'verified' | 'not-required'`. The guard rejects any session lacking `verified` once the user is enrolled or required, including sessions created before MFA. Success regenerates the session ID.

TOTP secrets are AES-256-GCM ciphertext (`v1:` format, user ID as associated data) under MFA_ENCRYPTION_KEY. The key is validated structurally in validateEnvironment and required by MfaService in production. Never log, return or audit a secret after enrolment. Recovery codes are stored only as Argon2id hashes and consumed with a conditional update. TOTP replay is blocked by the conditional `lastUsedStep` update. Code checks use the shared login_attempts counters. Five failures per user per 15 minutes, across sessions, start a lock: 429 even for correct codes, with one MFA_LOCKED_OUT event per lock. The lock lasts 15 minutes the first time and 1 hour on repeats; the series resets after a quiet day or an admin reset. Never lengthen it further or add a permanent lock: someone holding a password must not be able to cheaply deny the last administrator. TOTP accepts only the current and previous step. Enrolment services re-read mfaPending (stage enrol, unexpired, same user/authVersion) or require a full session. Revocation uses the shared revokeUserSessions helper (full and pending rows). Enabling, disabling and admin reset increment authVersion and delete all of the user's sessions, including pending ones, in the same transaction; then re-establish only the acting session. Admin reset takes the user-administration advisory lock, rechecks that the actor is an active administrator, refuses self-reset and never exposes secrets. Do not weaken the last-active-administrator rules. staff_security_events holds metadata only.

StaffMfa1792720000000 is additive and previous-version-compatible. Its rollback refuses while enrolments, recovery codes or security events exist. Deploy web before API because the login response may be `{ mfa, landingPage }`. A new authenticator (NewAuthenticator1793120000000; designed as the New authenticator group and approved 2026-11-09): anyone using an authenticator, administrators included, starts one from Account security with POST auth/mfa/replacement and a current or recovery code (used up), or with no code once within 15 minutes after signing in with a recovery code (session.mfaRecoveredAt, cleared on use); the sign-in offers it straight away after a recovery code. The setup limit is checked before the code, so a refused start never spends a recovery code. The new secret waits sealed in staff_mfa.pendingSecretCiphertext (15 minutes) while the old one keeps working, until POST auth/mfa/replacement/confirm with its first code and the replacementId the start returned (a hash of that sealed secret) swaps them under the user lock. A start made again elsewhere replaces the pending secret, so confirming an earlier one answers 409 before its code is checked or counted toward the lockout. The swap keeps the recovery codes, revokes every session, writes MFA_AUTHENTICATOR_REPLACED and continues this session. Email-code users and people without two-step verification can't use it. The web shows Not available yet when the route answers 404 (an older API); deploy the API first. Trusted devices (skipping the code for 30 days) are described under "Trusted devices and paper scans". SMS codes, WebAuthn and key rotation are not implemented; add them only with a separate request.

Email codes (EmailMfa1792790000000): staff_mfa.method is TOTP or EMAIL (EMAIL rows have no secret). SYSTEM_ADMIN may never use EMAIL: enrolment refuses it, and promoting an email-code user to administrator removes that enrolment in the same transaction so they set up an authenticator at the next sign-in. Administrators never complete a code check with an emailed code: if one still has an EMAIL enrolment (an older instance during a deploy, a manual role change), a correct password removes it with its recovery and outstanding codes, revokes their sessions and continues to authenticator setup (MFA_RESET_BY_ADMIN with no actor, reason administrator-sign-in). Codes are 6 digits, sent only to the account email through EmailService.sendStaffCode, stored only as SHA-256 hashes bound to user and purpose (login, enrol, manage) in staff_mfa_email_codes (one outstanding per purpose), expire after 10 minutes, are consumed atomically once, and never satisfy another purpose. Resends wait 30 seconds; at most 5 sends per user per 15 minutes; a failed send deletes the code and returns 503. Wrong codes use the same per-user lockout as TOTP. The verify step is POST auth/mfa/challenge (sends the login code), setup lists GET auth/mfa/methods, and Account security confirms changes with POST auth/mfa/email-code. Emails contain only the code and what it is for. Staff codes are sent from STAFF_EMAIL_FROM (a Gmail "Send mail as" alias of the SMTP mailbox), never the applicant EMAIL_FROM; validateEnvironment refuses the same address. Without EMAIL_DELIVERY=smtp and STAFF_EMAIL_FROM email codes are unavailable (never logged or shown instead). The web treats a 404 from these routes as an older API (authenticator only); deploy web before API. The rollback refuses while email enrolments exist. Google SSO must keep enforcing this policy (see docs/identity-architecture.md). Integration tests enrol fictional admins with test/mfa-helpers.ts in a *_test database only.

## Staff passwords
Designed in the Design System (StaffAddGeneratedScreen, StaffPasswordReadyScreen, StaffResetPasswordScreen) and approved by the user 2026-11-03: the web no longer asks an administrator to type a password. POST users without a password, or PATCH users/:id with generatePassword (never for your own account), makes one in the API (generatePassword in auth/password.ts: 16 characters with no lookalikes) and returns it once as generatedPassword; only its hash is stored, and it never goes in logs or events. PasswordReadyDialog holds it in memory until closed and asks before leaving while it is uncopied. The administrator sends it themselves; emailing it isn't authorized. A typed password from an older page is still accepted. Deploy the API first, because an older API refuses a create with no password.

Admin create, and an admin setting another user's password, set users.mustChangePassword. A correct password then stores only session.mfaPending with stage 'password' (10 minutes), admitted only by @AllowPendingPasswordChange on POST /auth/password. The guard rejects full sessions while the flag is set. The change requires the current password, the shared 12–128 rule and a different password, and is limited to 5 per user per 15 minutes. It bumps authVersion, deletes all of the user's sessions, and then either continues to MFA (forced flow) or re-establishes only the acting session. Bootstrap and seed accounts have the flag false. User administration revokes sessions only for real email/role/status/password changes. It writes metadata-only staff_security_events (USER_* and PASSWORD_CHANGED, field names only) in the same transaction. Create and update both take advisory lock 42002026 and recheck the actor. StaffPasswordChange1792760000000 rollback refuses while any flag is true. Deploy web before API. Residual risk: whoever uses an admin-set password first can change it; a one-time setup link would remove admin-known passwords and needs a separate request.

## Frontend backend connectivity
The BFF permits up to 90 seconds per upstream request and declares maxDuration=120 for Render Free wakeup; use Vercel Fluid Compute. Never retry mutations automatically, relax CSRF, or bypass sessions to mask outages. readBackendConfig validates HTTPS origins in production (no path, credentials, query or fragment) and header-safe BFF secret formatting. Logs must contain only allowlisted backendFailureCode results, never exception objects/messages, environment values, paths containing applicant tokens, credentials or cookies. Runtime logs distinguish configuration, timeout, network and generic failures. Changes require frontend redeployment; do not deploy without authorization. Longer proxy deadlines cannot fix an unavailable Render service and authenticated SSR retains its separate bounded timeout. Client mutations go through lib/client-api.ts, which maps network, 401, 409, 413 and gateway failures to typed ApiError kinds with friendly copy and never shows raw TypeError/SyntaxError text. Server pages validate key responses with lib/api-schemas.ts. Format dates with the LocalTime component, not toLocaleString in server-rendered code. parseResponse returns the parsed value, so every schema stays a z.looseObject (unknown fields kept); an optional field from a newer or older API may use .catch() so a bad value is dropped instead of failing the page, and status label maps need a neutral fallback for unknown statuses. Pages holding a one-time value (an uncopied invitation link) register useLeaveGuard as well as beforeunload, because shell navigation never fires beforeunload. Anything that marks notifications read calls router.refresh() so the bell and sidebar counts update.

## Production email delivery
Read docs/email-delivery.md. EmailService (modules/email) sends applicant verification codes over SMTP with Nodemailer when EMAIL_DELIVERY=smtp; production uses a dedicated Google Workspace mailbox with an app password. begin() generates a code (generateVerificationCode) only for a matched challenge and stores only its hash. Matched and unmatched requests must keep identical responses and the same single pre-response write (the challenge row); everything else (openedAt, sending, the VERIFICATION_EMAIL_SENT/FAILED outcome event) runs after the response through EmailService.runInBackground, which shutdown drains. sendVerificationCode retries transient failures, never retries EAUTH/EENVELOPE/EMESSAGE, and never throws. Unmatched requests send nothing. Emails contain only the code and expiry guidance, never invitation links, tokens, references or applicant data. Log only allowlisted Nodemailer failure codes (deliveryFailureCode), never addresses, codes, credentials or server replies. validateEnvironment must keep: authenticated TLS on 465/587 in production; outside production only a localhost inbox (Mailpit), never a real mail server; a single anchored EMAIL_FROM address without line breaks. Development and tests stay fictional-only (example.test) even with SMTP. Production without SMTP fails closed (503). begin() reports delivery ('email' or 'manual'), which drives the applicant guidance. SMTP credentials live only in the hosting provider's secret settings. Applicant status updates (below), staff two-step verification codes, driver link codes (applications, renewals, catch-up links, and contract links for the driver or a truck owner’s signer; see "Safety drivers" and "Units, existing drivers and Ready for the road") and Safety expiration reminders (to drivers, and to Safety staff not on Telegram; see "Safety compliance") are the only other authorized email types; do not add others (invitation links, other staff notifications) without a separate request.

Designed in the Design System (section 34, Existing drivers and Units, revised 2026-11-12; section 39, Safety follow-ups from staff answers: Rules by license, Driver application, Role names, Contracts, Ready for the road) and approved by the user 2026-11-12; Almaz (Samsara installs) has no sign-in.
- **Role names:** pages and messages call SAFETY_MANAGER the Safety Director and SAFETY_STAFF a Safety Manager (the driver's Safety contact). Code, roles, routes and tables keep their names; only the words changed.
- **Rules by license** (LicenseRules1793180000000, license-rules.ts licenseRules/rulesFor): CDL drivers need the DOT drug test, the Clearinghouse query and a PSP report (POST safety/drivers/:id/psp, with the signed PSP form or a confirmed paper one; PSP_UPLOADED), and their CDL stands in for the road test; a DL driver (pickups with a trailer up to 26,000 lb) needs no Clearinghouse or PSP (unless they once held a CDL) but a road test with its certificate (POST .../road-test, a driver_reports ROAD_TEST row). The consent kinds PSP_AUTHORIZATION, DOT_TESTING_AUTHORIZATION and APPLICATION_CERTIFICATION apply by license (appliesTo). The application adds Safety's packet answers (other names, ever held a CDL, English, the medical examiner and registry number, a DOT positive test and its follow-up, which only result viewers see, with RETURN_TO_DUTY papers), a minimum age of 21 and the medical card for every license. Clearance gaps follow the license.
- **Units** (Units1793190000000, units.service.ts, Safety › Units with Trucks, Trailers and Owners tabs): driver_trucks is the units table (kind SEMI, PICKUP or TRAILER; owned by a truck owner in truck_owners, an owner-operator, or the company for its trailers only), so an older API reading owner-operators' trucks keeps working. Numbers are unique among current units and handed out in order under advisory lock 42002040 (trailers T-<n>). Dates only: registration expiration, the last yearly inspection and each permit the type carries (PERMITS_FOR: every one for a semi, New Mexico for a pickup). Expiring documents lists unit dates; the Dec 31 permits are renewed together on Expiring documents › Permits. Optional copies of a paper (unit_files, units/<unit>/<kind>/<file>.pdf) are recorded when opened. Every Safety role reads units and may add one; changes are for Safety leads, the Safety Director, administrators, the unit's responsible Safety Manager and an owner-operator's Safety Manager. Unit reminders (UNIT_REGISTRATION, UNIT_INSPECTION, UNIT_PERMIT, staff only) go to the responsible Safety Manager, else the Safety Director. Dispatch picks the truck and trailer from Units when assigning (driver_assignments.unitId and trailerId; the free-text truck stays for older readers). A file adds units too (UnitsImportService: POST safety/units/check writes nothing; units/add rechecks under the number lock): a VIN already here is Already here, a number or VIN twice is a problem on the later row, and an owner the lists don't know is a choice that may add a new truck owner. units/check and units/add are 1 MB routes.
- **Existing drivers** (ExistingDrivers1793200000000, existing-drivers.ts, Safety › Drivers › Add existing drivers): drivers already on the road are added from their paper file as Cleared by the Safety Director or an administrator (adding them stands in for the decision), from a file (check and add, advisory lock 42002041) or one at a time, with nobody messaged and no application. existing_driver_records keeps who added them, the file's name and the hire date. Their license, medical card and work authorization dates are driver_documents rows with fromPaper (no file, no fingerprint, already checked), so holds, Expiring documents and reminders work at once; an expired one puts them on hold. A last yearly review from the paper file is a driver_annual_reviews row with fromPaper; with none, the review is due from the day they were added. The paper file checklist (driver_paper_items: APPLICATION, MVR_AT_HIRE, ROAD_TEST, PREVIOUS_EMPLOYERS, DRUG_TEST, CLEARINGHOUSE, MEDICAL_REGISTRY, E_VERIFY, those the license and type call for) is confirmed by the Safety Director, administrators or the driver's Safety Manager: on file (with a date), not on file with a note, or not needed (road test and previous employers only). The drug test and Clearinghouse items follow the test results rule (safety/results.ts), on the profile and in the list's counts. A catch-up link (driver_links purpose CATCH_UP, 14 days, bound to their email, CatchUpService) opens only photos of their current documents and the current consent forms; the scans wait unchecked like renewal scans while the paper dates keep counting, and sending closes the link. Safety's Verify accepts their scans without an application. Drivers › Missing details lists what each still needs. Never SSNs, license numbers, birth dates, test results or medical details.
- **Contracts** (RoadReady1793210000000, contracts.ts): the Driver and Contractor Acknowledgement is a consent form kind (CONTRACTOR_ACKNOWLEDGEMENT, published on Forms and letters with the driver's name, address and signature and the truck owner's signer's signature and title) that no application or catch-up asks for. For a driver on a truck owner's truck, Safety leads, the Safety Director, administrators and the driver's Safety Manager send the driver a link (purpose CONTRACT), then, once the driver signed, a link bound to the email on the owner's page (purpose CONTRACT_OWNER). Both are driver links with the emailed code, 7 days, opening only that document (ContractsService). driver_contracts keeps both signatures with their evidence; a trigger makes signatures append-only, and cancelling works until the owner signs. The signed copy is the version plus the certificate, with the owner's signer as countersigner (title and company). Paper contracts with a truck owner (the IC agreement, the equipment lease, a receipt per truck, others) are uploaded signed with their date (owner_contract_files, truck-owners/<owner>/contracts/<kind>/<file>.pdf, swept like other files); terms, pay, tax IDs and bank details never enter the workspace. Truck owners have no sign-in.
- **Ready for the road** (road-ready.ts): clearing a driver starts it (driver_road_ready; drivers cleared earlier and drivers added from paper have none). Eight steps: the unit (Dispatch's, else Safety's pick before Dispatch assigns), the acknowledgement (not needed for an owner-operator), the permits (from the unit), and by hand the binder and accident kit, the Samsara camera (in progress needs a note), decals, orientation and the truck's Telegram group (driver_road_ready_steps). Nothing here holds a driver; Dispatch and Drivers › Getting ready show it until every step is done. Once the group is made, a new dispatcher, a new truck or the driver leaving asks their Safety Manager (their last one, after they leave) to update it by hand (telegram_group_changes, askGroupChange, in the transaction that makes the change); the workspace can't change Telegram groups. Events hold steps, statuses and flags only, never notes, names or addresses.
Rollbacks refuse while any of their rows or events exist. Deploy the API first (new routes, kinds and fields).
